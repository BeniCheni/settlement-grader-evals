# The LLM judges package

The deliverables for Week 2 of the AI Agent Evals course: three judges validated against human labels, and one A/B
decision. Assembled by the PM seat (Claude) on Mon 2 Nov 2026. The notes below say who wrote each file or that a command generated
it. The acceptance items are the course's words, from its repository at commit
`51a59c2f6c9bb55806da764aaf585884b811a747`, under `week-02-designing-reliable-llm-judges/assignments/`.

**In sample, every figure in Assignments 1 and 2.** Assignment 1's final labels were adjudicated after the owner saw the judge's
verdicts, and Assignment 2's change was chosen by reading the same 32 tickets it was tested on. These files show how the
judges compare with the owner's labels on these rows and what one change did to these tickets, not how either would do on
ones it has not seen. Step 9, below, tightened one rubric and checked it on labels made afterwards. It is held out only
in a narrow sense, and it did not work.

## Step 9: the weakest judge again

The course does not ask for this. It follows Assignment 1's pitfall "Keep a held-out slice if you iterate".
`rule_adherence` answered FAIL on all 40 rows of set 1, so its rubric was tightened once and checked on 32 rows the owner
labelled afterwards. **It did not work: the judge answered FAIL on all 32 again, and the rubric misses the bar.**

| Measure | Result | Bar |
|---|---|---|
| Agreement | 17 of 32 (53.1%) | At least 85% |
| Kappa | 0.00 | At least 0.6 |
| False passes | 0 | Each one read |
| False fails | 15 | |
| Replies the harness could not parse (`UNPARSED`) | 0 | |

A judge with one answer has a kappa of 0 on any labels that hold both answers, and its agreement is just the share of rows
the owner labelled FAIL. The judge passed no row, so there are zero false passes. `UNPARSED` counts only replies with no verdict the harness
can read: all 32 replies have a blank second line where the rubric asks for `Reason:`, and 13 of their reasons run to 20
words or more where it asks for under 20. Neither changes a verdict or a figure.

## How to check it

Run these from the repository root. The first writes four files in `assignment-1/` and leaves `diagnosis.md` alone. The
second rebuilds the A/B page, and the third copies it here. The fourth rebuilds step 9's report in `reports/`. No command
here calls a model.

```bash
python3 -m scorer.judge export-course --labels labels/set1.jsonl --final labels/set1-final.jsonl --readings labels/set1-readings.json --provenance labels/set1-provenance.txt --verdicts judgments/set1-llama3.1-8b --rubrics rubrics --rubric-provenance labels/set1-rubric-provenance.json --out packages/llm-judges/assignment-1
python3 -m scorer.judge ab --a traces/ab-a --b traces/ab-b --verdicts judgments/ab --thresholds packages/llm-judges/assignment-2/thresholds.json --statement packages/llm-judges/assignment-2/statement.txt --set1 reports/judge-set1.json --cases data/gold.json --html reports/ab.html
cp reports/ab.html packages/llm-judges/assignment-2/comparison.html
python3 -m scorer.judge report --labels labels/set2.jsonl --readings labels/set2-readings.json --provenance labels/set2-provenance.txt --rubric-provenance labels/set2-rubric-provenance.json --verdicts judgments/set2-llama3.1-8b --md reports/judge-set2.md --json reports/judge-set2.json --html reports/judge-set2.html
```

`assignment-1/results.md` and both `comparison.html` files match their reports in `reports/` byte for byte, and these
commands should leave `git status` empty.

To see that the thresholds came first, compare the commit that added them with the commit that added the runs:

```bash
git log --follow --format='%h %ad %s' --date=iso -- packages/llm-judges/assignment-2/thresholds.json
git log --format='%h %ad %s' --date=iso -- traces/ab-b/run_meta.json
```

To see that step 9's rubric came before its labels, and its labels before its verdicts, read this from the bottom up:

```bash
git log --format='%h %ad %s' --date=iso -- rubrics-set2/rule_adherence.md labels/set2.jsonl judgments/set2-llama3.1-8b/judge_meta.json
```
