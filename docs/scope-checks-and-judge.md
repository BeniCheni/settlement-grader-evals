# Scope: the checks, the judge, and the proof they can be trusted

Written Wed 28 Oct 2026. Everything here is read from this repo on that day; the commands that
reproduce each number are next to it.

## The rule this stage exists to keep

No check and no judge decides anything on its own until it has been compared with labels a human
made: agreement of at least 85%, Cohen's kappa of at least 0.6, and every false pass (a real failure
it let through) read. A number that moves between two identical runs is noise, and a change smaller
than the noise has not been shown to do anything.

## Slice 1: what it delivers

Specified in `docs/slice-1-spec.md` and built by Cursor from it (`docs/cursor-prompts/slice-1-build.md`). The PM seat keeps
a prototype as a reference; its output is `data/oracle_slice1.json`, which the build must reproduce. The prototype is not in this
repo, so everything below is the contract and not yet code on `main`.

| Piece | What it does |
|---|---|
| `scorer/checks.py` | One plain-code check for each of the 11 failure codes code can decide. Each takes a recorded ticket and the answer key and returns evidence, or nothing. |
| `scorer/calibrate.py` | Compares every check with the failures a human labelled in `data/codes_v1.json`: agreement, kappa, false passes, false fails. |
| `scorer/score.py` | Score one run: which failure codes each ticket shows. (Comparing two runs is slice 2.) |
| `scorer/stats.py` | The arithmetic, tested against two worked tables whose answers were computed by hand. |
| `scorer/report.py`, `reports/calibration-v1.*` | The calibration as a page, in the Haunted Ledger style, regenerated by one command. |
| `ui/ledger.css` | The tokens and primitives every UI here uses. One file; no UI carries its own palette. |
| `data/calibration_readings_v1.json` | A written reading for every disagreement. A test fails if one has none. |

Accepted when these work and reproduce the oracle: `python3 -m scorer.calibrate traces/v1`,
`python3 -m scorer.report traces/v1 --out reports/calibration-v1.html`, `python3 -m unittest discover -t . -s tests`.

## What the prototype found

- **In sample, all 11 checks clear the bar.** Agreement 97% to 100%, kappa 0.89 to 1.00, no false passes.
  The two disagreements are `B01` (a net of 0.0 written where `settle_ticket` returned null) and `A02`
  (a final answer with no legs key). Both are literal by each code's own wording, so the check is right and
  the labels are short. The reading for each is in `data/calibration_readings_v1.json`; the labels are not
  edited here.
- **In sample is the catch.** Two checks were fixed while reading these same 32 traces (`WRONG_NON_GRADE` compared
  the net as well as the result; `GRADE_CONTRADICTS_FACTS` ignored the scores `find_match` returns when the grader
  never called `get_match_facts`, as on `X01`). That is tuning on the test set. The result shows the checks
  reproduce the labels they were built from.
- **The noise floor is not zero.** A local re-run of the same 32 tickets (same model, temperature 0, same frozen
  facts, not committed) matched 10 against v1's 11. Five tickets changed outcome (B01, B05, B10, C06, C09) and code
  counts moved by up to 2 (`NO_FINAL_ANSWER` 3 to 1, `OUTPUT_LIMIT_SPRAY` 2 to 0, `RULE_TOPIC_MISS` 3 to 5).
  Measured with the prototype's compare tool, which slice 2 builds properly. One pair is a hint, not a floor.

## Decisions that are not ours to make

1. **Which model judges.** It must be a different family from `qwen3:8b`, or the judge shares the grader's blind spots.
   A local model from another family that fits this machine costs nothing and keeps the repo dependency-free. A hosted
   model needs a key and a few dollars and is probably stronger. The judge code will take either through one adapter;
   the choice sets what a stranger needs to reproduce the result.
2. **The two label additions.** `B01` and `A02`, in `data/codes_v1.json`. PR #1 landed on 28 Oct (`6c5ceb7`), so the file is free to edit.
3. **Whether to spend the machine time on slice 2 now.** About ten minutes per run at the median wall clock.
4. **How many held-out tickets to label.** All 32 is the clean answer; the tickets the checks flag differently between
   runs plus a random dozen is the cheap one.

## Rules for every UI here

- It uses `ui/ledger.css` and nothing else for colour and type. Ink speaks, slime confirms, lamp marks where data came
  from and nothing else, blood alarms.
- A label earns its place only if it changes what the reader can do. No always-green status chips, no "local mode"
  banners, no tags that restate the page.
- Both themes, AA contrast on every text pair (computed, not eyeballed), reduced motion respected, and at 360, 375, 390
  and about 1000 px the page's `scrollWidth` equals its `innerWidth`. The viewport is set before any capture.
- A page that claims a result carries its provenance and its limits on the page, not in a README.

## Out of scope here

Red-teaming the slip-text injection and the over-block rate (next stage), growing the set past 32 tickets and the
confidence intervals that follow, verifying the 28 remaining answer keys, and fine-tuning anything.
